# FlowZenit V2 engineering rules

- Preserve the existing React/Vite, JavaScript, Supabase, and Vercel architecture unless an approved SPEC explicitly changes it.
- Documentation for Draft SPECs may be created or revised without a registered or approved batch. This includes `$speckit-specify`, `$speckit-clarify`, `$speckit-plan`, `$speckit-tasks`, `$speckit-analyze`, checklists, roadmaps, and planning documentation.
- Documentation commands do not approve a SPEC, change an approved decision, approve a batch, or authorize implementation. SPECs remain `Draft` unless the user explicitly approves a status change.
- Implementing a SPEC requires an exact, explicitly user-authorized, approved SDD batch manifest and immutable SPEC version. Never add, reorder, or replace a SPEC in that manifest.
- Execute SPECs in manifest order within each approved batch. Across separate batches, an independent SPEC may proceed when all of its declared dependencies are completed, its exact manifest is approved, the same SPEC is not active elsewhere, and writable file scopes are disjoint. An unrelated paused batch does not block that work. A paused batch remains paused and requires explicit privileged authorization to resume; independent work never changes its state or manifest.
- In FlowZenit, `$speckit-implement` is not a standalone implementation path; execute implementation only through `$sdd-run <batch-id>` after its admission checks pass.
- Parallelize only independent tasks with disjoint file scopes. Apply the same disjoint-scope check across separate active batches. Record assignments, results, and evidence in Supabase.
- Do not execute approval, limit-extension, or resume RPCs through the runner credential. These actions use the privileged Supabase SQL channel after explicit user authorization.
- A quality-gate waiver also requires the privileged Supabase SQL channel and exact owner authorization. Eligibility comes only from the immutable SPEC snapshot's optional `## Gate waiver policies` table in `plan.md`; missing entries mean `NEVER`. Runner tooling may validate and prepare exact SQL but must not execute it.
- Enforce the 5-attempt and 120-minute-per-SPEC correction limits. Count overlapping correction windows once, preserve counters across sessions, and pause the entire batch at either limit.
- Never place credentials, tokens, chat transcripts, or private prompts in SPEC snapshots, checkpoints, audit details, CLI output, or source control.
- Use physically isolated database tests by default. Owner-authorized synthetic fixture tests for SPEC-003@4, SPEC-004@2, SPEC-008@2, SPEC-009@2, and the current SPEC-006–SPEC-015 execution may use the existing FlowZenit V2 development Supabase project `flowzenithv2` (`twikxeloeftczwbpjvzr`) because this MVP uses the hosted Supabase project as its database test target. Before each test write, verify the exact project, schema, permissions, and absence of the run-specific fixture marker. Use synthetic records only; record all created IDs and parent relationships; run writes inside a transaction and roll back where supported, otherwise clean up only captured IDs in dependency order. Preserve every preexisting record and never use agent endpoints for these direct contract tests. For SPEC-008@2 and SPEC-009@2, test the runtime data path through the existing Supabase client/PostgREST; SQL MCP may assist preflight but does not replace this evidence. For SPEC-003@4, SQL MCP validates database behavior and Node doubles validate the adapter; a test-only direct Node pg URL/certificate is not required. This exception is limited to SPEC-003@4, SPEC-004@2, SPEC-008@2, SPEC-009@2, and SPEC-006@1 through SPEC-015@1 in this requested execution; it does not authorize permanent schema, migration, grant/RLS, production behavior, or deployment changes and does not change the default for other SPECs.
- Run the applicable lint, build, unit, integration, security, and acceptance checks. Report commands and real results; do not infer a pass.
- Do not commit, push, merge, deploy, reset, or discard user changes. The user performs version-control publication manually.

## SDD entrypoints

- Draft documentation: `$speckit-specify`, `$speckit-clarify`, `$speckit-plan`, `$speckit-tasks`, and `$speckit-analyze`; these do not require a batch or change SPEC/decision approval state.
- Functional implementation: `$sdd-run <batch-id>` only, after exact-manifest admission checks. `$speckit-implement` is not a standalone entrypoint.
- Operational commands: `npm run sdd -- help`.
- SDD operational state lives in the Supabase `sdd` schema. Local files hold SPEC source, Draft planning documents, governance documentation, and migration source code.
